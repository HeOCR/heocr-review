# Private handwriting intake

The feature has no production bindings, flag, cron, or static form. The main review database and its migration directory are separate from intake. Keep collection disabled until eval confirms the writer-level sampling and split check and the lead authorizes launch. A later DEV pilot needs its own writers, prompts, storage and campaign keys, outside the release candidate pool.

## Private configuration

- Use a dedicated D1 database for `HANDWRITING_DB` and the migrations in `intake/migrations`. Use separate private R2 buckets for `HANDWRITING_MEDIA` and `HANDWRITING_CONTROL`. Neither bucket should have a public URL or domain. Keep `HANDWRITING_KEY` in the Worker secret store. It keys the token, receipt and participant pseudonym digests. Use a campaign-specific key and preserve it through authorized restores.
- Place `configuration.json` in control storage. The `campaign` is an opaque storage namespace. Supply `writerConsent` and `readerConsent` with separately pinned `he` and `en` entries, each with `version`, `text` and its UTF-8 `sha256`. Supply the matching bilingual `retentionNotice`, including the approved backup expiry. Preserve immutable copies of the issued text versions and rights evidence privately.
- Pin `prompts` by packet ID with exact text, `sha256` and rights evidence. Configure `slots` with one prompt ID and approved capture, pen and paper assignment for each reserved writer. Eval owns the allocation, reserves and replacement rules. Keep the approved prompts, allocation and agreement evidence out of Git and ordinary reviewer records.
- Set the explicit `access` allowlists for `operator`, `intake`, `reader`, `adjudicator` and `eval`. Use the existing signed reviewer accounts for staff and readers. A writer needs an opaque, non-contact writer key, source key and reviewer pseudonym so the Worker can rule out self-review. Keep any contact mapping outside this system.
- After authorization, configure `launch.evalSampling`, `launch.evalSplit` and `launch.leadApproval` as references to the private approval records. A separate change can then set `HANDWRITING_INTAKE_ENABLED=1`. Verify disabled routes on both hostnames first. Production intake accepts only the canonical custom origin. Fixtures run on loopback without production approvals or any live data.

## Collect and review

All API paths below are relative to `/api/handwriting-intake`. Send JSON and the canonical `Origin` on staff writes through an authenticated same-origin session.

1. The operator calls `POST /operator/invitations` with the assigned `slot`, `writerKey`, `sourceKey` and `writerReviewerId`. Deliver `/handwriting-intake#<token>` directly to that writer. A token expires after seven days. The upload form removes it from the address bar and uses it only in an authorization header. Only send the original JPEG or PNG, up to 12 MiB, 12,000 pixels per dimension and 40 million pixels. Identify suitable source formats before issuing phone assignments.
2. The form displays the current private agreement in the writer’s language and requires an affirmative check. The exact agreement is recorded before the first write of the original. Resending the same file yields the same receipt. An accepted image can be replaced with a new invite from `POST /operator/pages/<page>/retake`. Deliver the new token privately. Previous pixels retire when the replacement becomes active, with version and hash lineage retained.
3. The intake reviewer uses `GET /intake/submissions` and `GET /intake/pages/<page>/versions/<version>/original`. Inspect the entire image and its surroundings. Send `privacy`, `rights` and `quality` as `clear` to the matching `/screen` action, or use `quarantine: true` for an unsuitable image. Reject a page with identifiers and ask for a retake.
4. In a private scratch directory, pin the exact original SHA and record ten ordered, original-raster pixel polygons. Display the raw raster orientation when drawing the polygons. Run `npx tsx scripts/prepare-handwriting-crops.ts <original> --sha256 <pin> --polygons <json-path> --output <new-private-file>`. For a replacement geometry, add `--replaces <current-geometry-id>`. Submit the resulting JSON to the version’s `/geometry` action. The tool re-encodes the raster, masks pixels outside each polygon and emits a mode-0600 payload outside the checkout. Verify the crops against the original before submitting. Delete scratch copies after private upload and include scratch in any withdrawal sweep.
5. Eval reads `GET /eval/lineage` and compares the restricted writer/source keys, image and crop hashes, geometry and retake lineage with its split records. A hold or unresolved match remains pending or overlap. For a cleared version, send its exact `geometryId` and `imageSha` with `status: "clear"` to `POST /eval/pages/<page>/versions/<version>/split`.
6. Readers use `/handwriting-intake/review`. They accept the current private reader agreement first. Reviewers type the visible line according to the private literal transcription instructions. Flag a suspected literal divergence or ambiguous line for independent adjudication. Geometry and privacy flags immediately remove the current crop from review. A changed crop set receives a fresh geometry ID, split check and two new blind reads. A private check routes an agreement that differs from the prompt to adjudication as well. The third reader submits an independent read before seeing earlier answers. Only after recording the adjudicated text or exclusion can they use the prompt for QC.

## Withdrawal and retention

Contrib monitors the project withdrawal inbox at `heocrproject@gmail.com` under lead oversight. Use the receipt code in the message, and keep the email, code and page identity out of logs and Git. With the operator session, send `{"receiptCode":"<code>"}` to `POST /operator/withdraw`. Check the response and repeat if necessary. An already published receipt requires the project’s approved post-publication reply.

The durable withdrawal record is written before removing active data. Confirm zero remaining active media, remove any authorized scratch and release-preparation copies, and confirm that the old invite, crop and candidate no longer serve. Allow in-flight requests to drain and rerun `POST /operator/reconcile` before confirming the cleanup to the writer. Report completion to the lead without the receipt code or identifying material.

Use `POST /operator/close` to freeze new uploads. Run `POST /operator/reconcile` as a daily operator check in the collection’s retention window, including the 90-day cutoff. It removes unreleased writer and reader consent evidence at the cutoff and keeps evidence pinned to released versions. Verify the private consent ledger with `GET /operator/consent`. Before serving a restored snapshot, keep the live control store attached, drain in-flight work and reconcile with the **current** withdrawal, close and publication records. Never roll that store back with intake data. Verify the cutoff and denial again before resuming access. Backup expiry comes from the approved retention notice.

## Candidate and publication

After closing, an operator can build a private candidate at `POST /operator/candidates`. Only active, split-cleared pages with ten resolved lines and consent are eligible. This generates a digest and dataset-local keys. Deliver neither originals nor private provenance with the candidate. Asset access is operator-only and verifies the stored image digest.

Under lead oversight, review rights and reviewer permissions for the exact manifest and aggregate the accepted pages and lines, withdrawals and exclusions. Obtain Shay’s separate approval for the exact release. Immediately before any authorized publication, re-read `GET /operator/candidates/<sha256>` and check every prepared asset against that manifest. Coordinate the final inbox check and release together. Discard any staged candidate invalidated by a withdrawal, geometry change, retake or split hold. After confirmed publication, pin the released version and manifest digest for each released page in the private control store at `<campaign>/published/<page>` as `{"version":"<version>","manifest":"<sha256>"}`. No Worker route publishes or changes those pins.
